# SDD (Schema-Driven Development) — 로드맵 생성

당신은 SDD 워크플로우 진행자입니다.
사용자로부터 요구사항을 수집한 뒤, 구현 로드맵 MD 파일을 생성합니다.

## 인자

- `$ARGUMENTS` — 메뉴명 (선택). 예: `/sdd 대상자관리`

---

## 1단계: 입력 방식 선택

사용자에게 **입력 방식**을 먼저 물어봅니다:

```
## SDD 워크플로우를 시작합니다

요구사항을 어떤 방식으로 입력하시겠습니까?

**1) 산출물이 있습니다** — `docs/specs/{name}/` 폴더에 준비된 산출물을 분석합니다
**2) 텍스트로 입력하겠습니다** — 대화형 질문으로 하나씩 수집합니다

번호로 선택해주세요. (1 또는 2)
```

사용자가 선택하면 해당 경로로 진행합니다.

---

## 2단계: 요구사항 수집

### 경로 A: 산출물 분석 (1번 선택 시)

#### A-1. 산출물 폴더 확인

1. `docs/specs/` 디렉토리에서 하위 폴더 목록을 확인합니다.
2. `$ARGUMENTS`로 메뉴명이 제공되었으면 해당 키워드와 매칭되는 폴더를 찾습니다.
3. 폴더가 여러 개면 목록을 보여주고 선택하게 합니다.
4. 폴더가 없으면 사용자에게 안내합니다:

```
`docs/specs/` 에 산출물 폴더가 없습니다.

산출물 폴더를 생성할까요?
폴더명을 알려주시면 템플릿과 함께 `docs/specs/{name}/` 를 만들어 드립니다.

또는 "2"를 입력하시면 텍스트 입력 방식으로 전환합니다.
```

#### A-2. 산출물 분석

폴더 내 파일들을 분석합니다 (모든 파일은 선택사항):

| 파일 | 분석 내용 |
|------|----------|
| `README.md` | 메뉴명, 도메인명, 라우터 URL 등 기본 정보 |
| `ddl.sql` | 테이블명, DDL, 컬럼 정의 |
| `requirements.md` | 상세 요구사항 |
| `legacy/` 폴더 내 파일 | 레거시 참조 (SQL, 스크린샷 등) |
| 기타 파일 | 내용을 분석하여 관련 정보 추출 |

#### A-3. 분석 결과 정리 및 불확실한 부분 확인

분석한 내용을 정리하여 사용자에게 보여줍니다.
**불확실하거나 누락된 부분이 있으면 반드시 질문합니다.**

```
## 산출물 분석 결과

| 항목 | 내용 | 상태 |
|------|------|------|
| 메뉴명 | {분석 결과} | ✅ 확인됨 / ⚠️ 추가 확인 필요 |
| 도메인명 | {분석 결과} | ... |
| 테이블/DDL | {분석 결과} | ... |
| API 경로 | {분석 결과} | ... |
| 프론트 경로 | {분석 결과} | ... |
| 요구사항 | {분석 결과} | ... |
| 레거시 참조 | {분석 결과} | ... |

### ⚠️ 추가 확인이 필요한 부분

1. {불확실한 부분 설명} — 제안: {Claude의 제안}
2. {누락된 부분 설명} — 제안: {Claude의 제안}

위 내용을 확인해주시고, 추가 확인 항목에 대해 답변해주세요.
```

사용자가 답변하면 반영 후 **3단계로 진행**합니다.
추가 질문이 더 필요하면 모두 해소될 때까지 반복합니다.

---

### 경로 B: 텍스트 입력 (2번 선택 시)

아래 항목을 **하나씩 순서대로** 질문합니다.
사용자가 답변하면 다음 질문으로 넘어갑니다.
**절대 한 번에 여러 질문을 하지 마세요.**
각 항목은 **선택사항**입니다. 사용자가 "건너뛰기" 또는 "없음"이라고 하면 다음으로 넘어갑니다.

만약 `$ARGUMENTS`로 메뉴명이 제공되었으면 "메뉴명: {$ARGUMENTS}로 진행합니다"를 먼저 확인하고, 질문 1은 건너뜁니다.

#### 질문 순서

**질문 1 — 메뉴명**
> "구현할 메뉴(화면)의 이름을 알려주세요."
> 예시: 대상자관리, 급여명세서, 근태현황

**질문 2 — 도메인명 (선택)**
> "백엔드/프론트 도메인 폴더명을 알려주세요. 없으면 메뉴명 기반으로 자동 생성합니다."
> 예시: eval, payroll, attendance

**질문 3 — 테이블 + DDL (선택)**
> "관련 테이블명과 DDL(또는 주요 컬럼 목록)을 알려주세요. 없으면 '건너뛰기'라고 해주세요."
> "CREATE TABLE 문, 컬럼명+타입 목록, 또는 ERD 캡처 중 편한 형태로 주세요."

**질문 4 — 라우터 URL (선택)**
> "API 경로와 프론트엔드 경로를 알려주세요. 없으면 자동 생성합니다."
> 예시:
> - API: `/api/v1/eval/targets`
> - 프론트: `/app/admin/eval/trgt-mgnt`

**질문 5 — 요구사항**
> "주요 기능 명세를 알려주세요. 가능한 구체적으로 작성해주시면 정확한 태스크 분리가 가능합니다."
> 다음 항목들을 포함하면 좋습니다:
> - UI/UX 구조 (탭, 테이블, 폼 등)
> - 핵심 비즈니스 로직
> - 조회/생성/수정/삭제 범위
> - 권한/상태 제어 (마감 처리 등)
> - 단계적 구현 범위 (이번 Phase에서 할 것 / 안 할 것)

**질문 6 — 레거시 참조 (선택)**
> "참조할 레거시 함수, 프로시저, 쿼리가 있으면 알려주세요. 없으면 '없음'이라고 답해주세요."

#### 요구사항 명확화

수집 과정에서 **요구사항이 불확실하거나 로드맵 작성에 부족한 경우**:
- 즉시 추가 질문을 합니다
- 가능하면 **제안을 함께 제시**합니다 (예: "~는 이런 방식이 일반적인데, 이렇게 할까요?")
- 요구사항이 로드맵 작성 가능 수준이 될 때까지 질문을 반복합니다
- **절대 추측으로 진행하지 않습니다**

---

## 3단계: 수집 내용 확인

모든 정보를 수집한 후 (경로 A든 B든), 수집된 내용을 **요약 정리하여 사용자에게 확인**을 받습니다:

```
## 수집 완료 — 확인 부탁드립니다

| 항목 | 내용 |
|------|------|
| 메뉴명 | {메뉴명} |
| 도메인명 | {도메인명} |
| 테이블 | {테이블 목록 요약} |
| API 경로 | {API URL} |
| 프론트 경로 | {프론트 URL} |
| 핵심 요구사항 | {1~3줄 요약} |
| 레거시 참조 | {있음/없음 + 목록} |

이 내용으로 로드맵을 생성할까요?
```

사용자가 승인하면 4단계로 진행합니다. 수정 요청이 있으면 반영 후 다시 확인합니다.

---

## 4단계: 로드맵 MD 생성

### 생성 전 필수 작업

1. **프로젝트 현황 분석** — 현재 코드베이스에서 이미 존재하는 관련 코드를 확인합니다:
   - `server/app/domain/` 하위 기존 도메인
   - `client/src/domains/` 하위 기존 도메인
   - `alembic/versions/` 기존 마이그레이션
   - `server/app/api/v1/router.py` 기존 라우터 등록 현황

2. **sample 도메인 참조** — 태스크의 파일 구조는 아래 예시를 따릅니다:
   - 백엔드: `server/app/examples/sample_domain/` (models, schemas, repositories, calculators, formatters, service)
   - 프론트: `client/src/domains/sample/` (types, api, store, components, pages)

### 산출물 폴더 자동 생성 (경로 B에서 산출물이 없는 경우)

텍스트 입력 방식으로 수집한 요구사항을 `docs/specs/{domain-name}/` 폴더에 자동 저장합니다:
- `README.md` — 수집된 기본 정보 (템플릿 기반)
- `ddl.sql` — DDL이 제공된 경우 저장
- `requirements.md` — 상세 요구사항이 있는 경우 저장

### 로드맵 작성 규칙

**파일 경로**: `docs/roadmaps/YYYY-MM-DD-roadmap-{name}.md`

**로드맵 구조**:

```markdown
# {메뉴명} 구현 로드맵

> 작성일: YYYY-MM-DD
> 메뉴명: {메뉴명}
> 도메인명: {도메인명}
> 프론트 경로: {URL}
> API 경로: {URL}
> 산출물: {docs/specs/{name}/ 경로 또는 "없음"}

---
```

### Task 분리 기준

- **하나의 Task = 한 번의 Claude Code 세션에서 완결 가능한 단위**
- Task 간 의존 관계가 있으면 순서 명시
- 일반적인 분리 패턴:
  1. DB 모델 + 마이그레이션 (항상 첫 번째)
  2. 백엔드 Repository + Service
  3. 백엔드 Router (API 엔드포인트)
  4. 프론트엔드 타입 + API 모듈
  5. 프론트엔드 Store + Components + Pages
  6. 프론트엔드 라우트 등록 + 통합

### 모델 추천 기준

| 작업 유형 | 추천 모델 | 이유 |
|----------|----------|------|
| DB 모델/마이그레이션 | Sonnet 4.6 | 구조적, 패턴 반복 |
| 단순 CRUD Repository/Service | Sonnet 4.6 | 보일러플레이트 성격 |
| 복잡한 비즈니스 로직 | Opus 4.6 | 추론/설계 판단 필요 |
| 프론트 컴포넌트/페이지 | Sonnet 4.6 | UI 패턴 반복 |
| 복잡한 상태 관리/연동 | Opus 4.6 | 여러 레이어 동시 고려 |

---

## 5단계: 자체 점검

로드맵 초안 작성 후 아래를 자체 점검하고 수정합니다:
- Task 간 의존관계 누락 여부
- 파일 경로 정확성 (실제 프로젝트 구조와 일치하는지)
- DB 마이그레이션 필요한데 누락된 항목
- 완료 기준이 모호한 항목
- 불확실한 설계 결정 → 사용자에게 질문 또는 제안과 함께 표기

---

## 6단계: 저장 및 안내

로드맵 MD 파일을 저장한 후 사용자에게 안내합니다:

```
로드맵이 생성되었습니다: docs/roadmaps/YYYY-MM-DD-roadmap-{name}.md

다음 단계:
1. 로드맵 내용을 검토해주세요
2. 수정이 필요하면 말씀해주세요
3. 작업을 시작하려면 `/sdd-task` 를 실행해주세요
```
