# 새 기능 추가

기능명: `$ARGUMENTS`

## 절차

### Step 1. 기능명 확인

인자로 기능명이 전달되지 않았으면 사용자에게 질문한다:

```
추가할 기능의 이름을 알려주세요.
예: 목표관리, 평가결과조회, 알림설정
```

### Step 2. 기존 요구사항 파일 확인

`docs/feature/` 폴더가 없으면 생성한다.
`docs/feature/{feature-name}.md` 파일이 이미 존재하는지 확인한다.

**파일이 존재하면:**
- 파일 내용을 읽고, 빈 항목이나 미완성 섹션이 있는지 확인
- 모든 필수 섹션이 채워져 있으면 → Step 4로 이동 (로드맵 작성)
- 미완성 항목이 있으면 → 사용자에게 어떤 부분이 비어있는지 안내

**파일이 없으면:**
- Step 3으로 이동하여 템플릿 생성

### Step 3. 요구사항 템플릿 생성

`docs/feature/{feature-name}.md` 파일을 생성한다.
기능의 특성을 고려하여 아래 기본 구조에 **AI가 판단한 추가 질문/선택지를 포함**한다.

**생성 시 AI 역발상 적용:**
- 기능명에서 추론 가능한 정보는 미리 채워넣는다 (예: "목표관리" → 화면 유형을 "탭 구조"로 제안)
- 해당 기능에 특화된 추가 질문을 섹션에 추가한다 (예: "평가" 관련이면 "평가 단계", "가중치" 질문 추가)
- 기존 도메인 구조(`server/app/domain/`)를 참고하여 관련 도메인이 있으면 연관 기능에 기재

**생성 후 안내:**

```
요구사항 템플릿이 생성되었습니다: docs/feature/{feature-name}.md

[작성 안내]
1. 위 파일을 열어 필수 항목(1~3번)을 채워주세요
2. 선택 항목(4~8번)은 해당되는 것만 작성하시면 됩니다
3. 작성 완료 후 /feature {feature-name} 을 다시 호출해주세요
```

### Step 4. 설계 검증 (로드맵 작성 전 필수)

요구사항 내용을 분석하여 아래 항목을 점검하고, 문제가 있으면 **로드맵 작성 전에** 사용자에게 보고한다.

#### 논리 오류 점검
- 요구사항 간 모순은 없는가? (예: "권한 없이 접근 가능" + "관리자만 삭제 가능")
- 데이터 흐름에 빠진 단계가 없는가? (예: 등록은 있는데 목록 조회가 없음)
- 비즈니스 규칙이 구현 가능한 형태인가?

#### 설계 함정 점검
- 기존 도메인/테이블과 이름이 충돌하지 않는가?
- N+1 쿼리나 성능 이슈가 예상되는 구조가 아닌가?
- 프로젝트 아키텍처(5계층)에 어긋나는 요구사항이 없는가?

#### 추가 확인 필요 사항
- 요구사항에서 암묵적으로 가정하고 있지만 명확하지 않은 부분
- 사용자의 의사결정이 필요한 선택지 (A안 vs B안)

**점검 결과 출력 형식:**

```markdown
## 설계 검증 결과

### 발견된 이슈 (해결 필요)
| # | 유형 | 내용 | 제안 |
|---|------|------|------|

### 확인 필요 사항
| # | 질문 | 선택지 |
|---|------|--------|

### 검증 통과
- 기존 도메인 충돌 없음
- 아키텍처 적합성 확인
- ...
```

이슈가 없으면 바로 Step 5로 진행한다.
이슈가 있으면 사용자가 해결/확인한 후 Step 5로 진행한다.

### Step 5. 로드맵 작성

요구사항 파일의 내용을 기반으로 로드맵을 작성한다.

**작성 전 사용자 최종 확인:**
```
요구사항을 확인했습니다. 아래 내용으로 로드맵을 작성할까요?

- 메뉴: {메뉴 경로}
- 화면 유형: {유형}
- 주요 기능: {목록}
- 관련 테이블: {테이블}

진행할까요? (수정사항이 있으면 말씀해주세요)
```

**승인 후:**
- `docs/roadmaps/` 폴더가 없으면 생성
- `docs/roadmaps/YYYY-MM-DD-roadmap-{feature-name}.md` 생성
- 기존 로드맵 형식(Phase → Task)과 동일
- 각 Task에 작업 모델(sonnet/opus) 명시

**로드맵에도 설계 검증 결과를 포함:**
- Step 4에서 발견된 이슈와 해결 내용을 로드맵 상단에 "설계 결정 사항" 섹션으로 기록
- 향후 태스크 실행 시 참고할 수 있도록

**로드맵 작성 완료 후 안내:**
```
로드맵이 생성되었습니다: docs/roadmaps/YYYY-MM-DD-roadmap-{feature-name}.md
작업을 시작하려면 /execute 를 호출하세요.
```

## 작업 중 소통 원칙

**작업 전·중·후 언제든** 아래 상황이 발생하면 즉시 사용자에게 알린다:
- 요구사항 해석에 애매한 부분이 있을 때
- 여러 구현 방법 중 선택이 필요할 때
- 기존 코드와 충돌이 예상될 때
- 원래 계획과 다른 방향으로 가야 할 때

묻지 않고 임의로 결정하지 않는다.

## 주의사항

- 5계층 아키텍처(Router→Service→Repository→Calculator→Formatter)를 반영하여 로드맵 작성
- 신규 테이블이 필요한 경우 Alembic 마이그레이션 Task를 Phase 1에 배치
- 도메인 간 직접 의존 금지 원칙 반영
- 프론트엔드 작업 시 `client/src/core/ui/` 기존 컴포넌트 활용을 Task에 명시
- 필요한 디렉토리(`docs/feature/`, `docs/roadmaps/` 등)가 없으면 자동 생성
